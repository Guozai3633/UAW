# 多session提交交接模板

复制字段到自己的 `handoffs/<session>.md`；不把整份模板当实现证据。开发session只写自己的提交，A的派发和接受记录统一写入 [DISPATCH.md](DISPATCH.md)。

## 基线信息（引用A的派发表）

- Session / 工作包 / 原轮：
- 真实基线提交SHA、分支及worktree：
- 基线schema版本/摘要、uv.lock摘要：
- 允许修改目录及必要例外：
- 已批准的公共接口提案：
- 可用测试环境 / 未满足依赖：
- 实际派发时间：

## 开发session：提交

- 分支 / 基线SHA / 本包提交SHA（或明确“尚无提交”）：
- 修改文件清单：
- 新增/改变的公开方法、请求/结果schema：
- 对接示例：一个成功、一个拒绝/失败、一个重复/版本冲突结果：
- 数据状态所有者 / 仓储命名空间 / CAS与幂等策略：
- 测试命令、实际环境、回执路径及结果：
- 验证的是纯组件、实际SQL、本机路径、真实外部模型中的哪些范围：
- 未运行/未通过项、替身与未实现依赖：
- 需要A修改的composition/迁移/契约/依赖：
- 对已合入基线的影响 / 可回退提交：

测试回执存 `tests/.artifacts/<session>/<工作包>/`，不覆盖共享的 `docs/implementation/evidence/`。

## A的审阅清单（在DISPATCH中填写结果）

- 修改是否在允许目录内，公共变更是否已通过提案：
- 在真实集成分支实际运行的验证命令/结果：
- 语义、权限、预算、取消、版本等组合风险：
- 冲突由谁修复、采用哪份策略及原因：
- 结论：退回修复 / 组件接受 / 需要真实环境后再验收：
- 合入方式与真实集成提交SHA：
- 下一包可用基线SHA / 原轮尚未通过的条件：

组件接受与原P0/P1轮次的accepted分开记录。未配置的提供方、尚未完成的配对或执行权限不能通过文案变成已可用。
