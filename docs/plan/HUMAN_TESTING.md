# 人工体验测试：与开发并行的固定版本验证

2026-10-13新增。用户明确要求：开发到可体验阶段主动启动，让用户亲自测试，反馈写回计划。
本计划补充现有模块/阶段/轮次，不替代自动化验收，也不新增 Runtime。

## 1. 什么时候安排

一个用户可以从页面完成的流程接通后，就安排体验；不等全项目完成或P5才开始。
聊天提交、理解提示、审批、取消、成果阅读、接受、刷新恢复、新材料入口等可分别体验。
每次产品流程新增或关键反馈修复后，准备新的固定版本。

自动检查回答“按契约能否执行”；本人体验回答“是否看得懂、好操作、结果是否值得用”。
模型自评、Playwright受控点击和开发人员代操作不算本人体验或用户接受。
体验发现的其他问题仍记录；不因本次预设范围之外而忽略用户反馈。

## 2. 模块—阶段—每轮任务

| 工作 | 触发阶段 | 每轮目标与任务 | 目录/交付 |
| --- | --- | --- | --- |
| H-准备 | 任一可操作流程接通 | A固定源码/前端dist/依赖/配置版本，核对可用场景与已知缺口；启动实际localhost前后端并预跑当前范围 | docs/implementation/human-tests/；固定版本和启动回执 |
| H-体验 | 准备范围通过后 | 用户本人从任务入口开始，使用自己的表达完成任务；记录迷惑、等待、失败、结果不满意和反复操作 | 同目录体验记录；用户原反馈，不写虚构结果 |
| H-修复 | 收到反馈即进入 | A定位并分派给原owner；B页面/交互，C工具/结果，D本机/授权，A来源/API/组装；能独立修的并行进行 | 原owner允许源码/测试目录；准确修复SHA和问题回执 |
| H-复体验 | 用户可见问题修复后 | A合入并做受影响回归，准备新固定版本；用户重试原场景，核对是否解决；保留上一版反馈和失败 | 新记录链接原问题，不覆盖旧回执 |
| H-阶段结论 | 原阶段门槛及体验范围满足 | 分开记录工程通过、体验结论、成果是否本人接受；尚未满意的核心流程保留未通过 | 当前阶段/轮次报告链接体验记录 |

普通后台组件包不每包打断用户。形成完整可体验路径后给一次明确入口和少量场景；
用户可以随时自由测试，修复不应一直等下一阶段。A继续不依赖反馈的开发，必要输入未到不代填。

## 3. 体验版本怎样隔离

默认采用固定commit＋不可移动测试标签（建议 human-hNN-vN），用独立测试工作区启动。
用户测试时该工作区不热合入浮动integration；开发会话继续原分支，不操作其环境。
测试服务只绑定localhost，前后端端口、数据库、状态目录、blob和日志均单独登记。
测试数据库/状态不得作为开发或已有用户历史的替代品；凭据使用既有受保护配置方式，
只在环境记录里写配置版本及可用性，不写令牌、cookie、launch秘密或完整材料正文。

标签给出“到底体验哪版”；worktree和独立服务/数据给出运行隔离。单独Git分支不能隔离数据库、端口或进程。
短体验不需要长期维护分支。需要数天维护或连续修补体验版时，建codex/human-hNN分支，
从固定版本开始；修复仍由原owner交到A集成，再把准确修复提交带到体验分支，避免双向各写一套功能。
准备独立测试工作区前先检查现有占用和用户未提交文件，不覆盖原工作目录或正在运行的用户任务。

从独立目录运行可能需要新的真实本机设备/目录授权；旧授权或launch不自动复制为新授权。
本人确认和成果接受必须用户操作，不代点、不把口头反馈自动转成产品内接受回执。
启动、可用性核对和隔离准备由A完成；原生弹窗只在用户明确方便时触发。

## 4. 启动与体验交付要求

A每次准备完成后给用户：

1. 固定版本/源码SHA，以及实际可打开的localhost页面链接。
2. 本次可以测试的流程、已知不可用范围；不显示虚构工具或成功状态。
3. 两三个任务建议和预期观察点，同时允许自由提问和自由操作。
4. 如何停止、拒绝、刷新继续，反馈怎样提交；需要本人操作时明确说明窗口和范围。

启动前实际检查后端、前端、认证来源、当前固定用户模型配置、事件重连和本次材料入口。
不能只启动端口就宣布可测试。失败记录停止位置；未具备来源的场景保留不可用。
无需等待所有未来能力完成；能体验的办公/学术文本流程可以先开放，文件链单独等待真实门槛。
需模型调用时沿用管理员现有配置和用户选定模型，记录失败、用量及pending费用。
没有本机执行或安装授权的能力继续关闭，不为方便体验自动开启flags。

## 6. 反馈记录模板

记录位于docs/implementation/human-tests/HNN-vN.md，启动时实际创建，至少包含：

- 固定源码、前端dist摘要、依赖锁、配置版本、服务端口/健康检查、真实/受控依赖说明。
- 本人操作时间、任务原要求的必要摘要、预期、实际结果、用户原反馈和具体页面/步骤。
- 工程结果、用户体验结果、产品内成果接受三栏分别记录，不互相代替。
- 任务/Run/Item/Artifact必要引用及受保护回执位置；不公开凭据或未经选择的材料。
- 总等待、核对、修正与导出时间；实际所有模型尝试/失败/用量和pending费用。
- 问题严重程度、所属模块/owner、修复提交、复体验版本/结论、仍未解决项。

阻止核心任务完成、结果丢失或错误接受的问题，修复后再评该场景通过。
文字/布局反馈可独立修复，优先级按真实影响记录，不随意编造分数或交付日期。
没有收到本人反馈标awaiting_user；用户未测试不能标通过，不阻止其他已授权独立开发。
