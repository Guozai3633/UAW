## 受理链路

认证用户 → 校验会话归属与请求结构 → 持久事务锁 → 核对 request_id/参数 → 读取当前平台配置与用户选择 → 保存 InputRecord、Item、Task、Run、固定绑定、根预算 → 写入有序事件 → 提交 → 返回 202。

202 表示已经受理。现在 Run 初态为 queued，没有执行器自动领取，也不会产生虚构 Agent 答案。Runtime `RunRuntime.create` 使用自己的 RunCreateRequest 与结果 envelope，保留可信入口提供的 InputRecord ID、turn_id 和原文。

会话模型必须由用户明确选择；绑定的 ResolvedModelPolicy 保存真实认证配置动作的 input 引用。原文和这些用户动作统一存于不可变 inputs 命名空间。不存在静默选择另一个模型或降低模型规格的分支。

相同请求和参数返回第一次受理回执；不同参数使用同一请求 ID 返回冲突。回执中的 Run 是受理快照，查看最新状态使用 runs.get/事件读取。事务中任意失败，原文、事件、预算及请求回执共同回滚。

附件摄取、项目绑定、跨会话任务修订、Auto 模型路由和记忆尚未实现，对应请求明确拒绝；不会默默忽略。

## 状态、事件与取消

- Run/Item 使用独立状态机。完成一条消息不会完成任务；worker 不能提交 completed、failed 或 cancelled 任务状态。语义完成控制器在后续阶段接入。
- 原始用户消息不可修改。执行交互项可按 CAS 从 pending → in_progress → completed 等允许分支更新，保持同一个 item ID，重复请求不会重复事件。
- 每次领域变化和事件在同一事务提交。事件载荷按 EventPayload 严格分支验证，可通过 payload_ref 对应的事件读取接口访问。
- 分页 cursor 绑定用户、会话、事件/Item 类型、水位和到期时间，并由独立密钥签名。Item 页面读取指定水位下最后一个版本；后续更新不会改写上一页的历史。历史读取没有工具调用路径。
- queued Run 可确定地取消并释放根额度。开始准备/运行后，取消只保存停止新动作的标记；没有收到真实执行器停止回执时，不冒充已经停止。
- 暂未实现 SSE、事件保留回收、完整执行恢复、子树取消和跨模块 checkpoint。

## 资源账本策略

1. 当前开发默认上限：输入 100000 tokens、输出 16000 tokens、模型 16 次、工具 32 次、子实例 4 个、最长 1 小时、5 USD、64 步、深度 2。它们是开发准入上限，**不是当前收费或模型价格**，也不会开启子 Agent。
2. 每个 attempt 独占一个子预留；CAS、事务锁及数据库唯一索引防止并发超订与同 attempt 重复占款。只有 preparing/running/verifying 状态可预留。
3. 调用意图提交后即标 billing_pending。重复提交意图返回 unchanged；执行器不能把旧回执当成再次调用的许可。
4. 调用失败也结算用量；Usage 关联 operation、trace、attempt 和 reservation。账本 API 不向用户/模型开放虚构使用量的写入口。
5. 未知费用和 Token 字段省略，保留对应估计额度。pending 不允许填写 money；estimated 仍不是最终账单。已发出或待核对的调用不能按未使用额度释放。
6. 确认账单时替换同 attempt 的待核对版本，扣除旧记录再加新记录，不重复计费，不允许抹掉已观察的资源。金额用精确 Decimal 和普通十进制字符串计算，覆盖九位小数。
7. 实际费用超过预留/总额仍如实记录，标 overdrawn，剩余显示零并阻止新准入/调用意图；不会把实际费用裁到预算上限。
8. 未发出的额度可以释放。调用意图之后的崩溃不能仅靠本轮账本恢复外部结果；P0-05/后续恢复协议负责核对，不重复发起动作。

本轮基础范围验收通过。Run 公共创建入口已经接入 composition；其他六个 Runtime 尚未绑定执行实现。下一步是 P0-05 固定模型真实调用，再接 Intent/Agent/Tool 循环；语义质量与成果完成仍未验收。
