# UAW 子 Agent 设计提示词与反馈协议

状态：v0.2 草案，尚未通过真实模型任务评测。创建定义统一通过 agents.create 工具，修改通过 agents.update，启动执行通过 agents.invoke。设计采用当前主 Agent 的工具循环：按需加载本提示词，提交工具参数，收到 Runtime 结果后继续对话。创建定义不要求完整复杂度评估、Planner 或 DAG。统一控制工具见 [CONTROL_TOOLS.md](../CONTROL_TOOLS.md)。

## 1. 精炼提示词正文

```text
按用户要求设计当前会话的子 Agent 并调用 agents.create；修改时调用 agents.update。
写清职责、适用/排除范围、简短工作指令和验收要求；不擅自增加用户未要求的角色。
技能与工具边界从可用目录选取；通用执行、权限和模型政策由 Runtime 继承，不重复写进角色指令。
用户未指定模型时设为 inherit；明确指定时保留原名称及输入引用；明确要求自动选择时设为 auto。
不要猜测模型是否可用、发明权限，或覆盖用户的模型选择；存在性由 Runtime 校验。
有足够信息且用户已要求创建/修改时，直接提交工具参数；只有关键歧义才询问。
收到失败反馈后修复可确定的配置错误；模型缺失/不可用时说明原因，只有用户允许替代才选候选。
根据已完成记录继续，避免重复创建；只宣告 Runtime 确认成功的定义，未解决项明确保留。
```

这段正文由 Agent Runtime 在用户提出创建、修改或停用定义时触发加载，由 Context Runtime 装配。不要每轮附带整个设计文档。输出类型/必填字段由动作 schema 约束，短提示词说明职责和行为即可。

## 2. 动态输入

仅提供本次用户原文及引用、当前会话、已有定义摘要/版本、可用技能和工具类别、可授予权限、当前模型继承政策，以及相关校验反馈。owner 和有效 conversation scope 由服务端取得，不相信模型自行提供的身份字段。

模型目录由 Model Runtime 管理，可提供简短候选名称/能力/可用状态；目录很大时按需查询，避免把全部模型说明塞入每次创建请求。候选必须当前用户可见，不泄露无权使用的目录信息。

## 3. 定义动作契约草案

LLM 使用 `agents.create` / `agents.update` 工具，统一经过 Tool Runtime 调用 Agent Runtime 的定义入口；定义版本与职责归 Agent Runtime，模型名称解析归 Model Runtime。原 `define_or_update_agent` 是早期动作草案，现不作为绕过 Tool Runtime 的独立执行通道。停用可使用有版本的 agents.update 配置 enabled=false；运行取消另用 agents.cancel。

创建参数包含 definitions 与 batch_policy；更新参数包含 definition_id、expected_version 和 patch。每个定义包含 name、description、instructions、use_when、avoid_when、skill_refs、tool_categories、output_contract、model_request。request_id、owner、有效会话作用域和默认用户输入来源由工具运行时注入，模型不能伪造；跨作用域需用户明确授权。

其中 `model_request` 仅提出用户模型意图，不是已解析配置：

```json
{
  "mode": "explicit",
  "requested_name": "用户原话指定的模型名称",
  "source_input_ref": "user-input-ref"
}
```

未指定模型使用 `inherit`，requested_name=null；用户明确授权该角色自动选模型使用 `auto`。`explicit` 的原名称即使不在目录也保留，供 Runtime 返回准确反馈；不能先改成 LLM 猜测的合法名称。服务端用用户原文和可信模型意图解析结果核对覆盖来源，有歧义则反馈澄清，不能只因模型填了 source_input_ref 就认为取得了授权。

角色指令保持简短，例如论文分析角色可写：

```text
负责阅读指定论文，提取论点、前提、证据与局限，回应用户的问题。
区分原文结论与待验证推测，引用定位到实际取得的版本和位置。
需要复现时提交明确的数据/实验要求；材料不足说明缺口。
交付可继续修改的研究笔记。
```

共同规则只由 Runtime 装配一次；长方法、模板和参考资料放 Skill，不把全部内容复制到每个定义。

## 4. 模型目录校验与返回当前 LLM

Model Runtime 校验当前用户目录、目录登记别名、可用状态和必要能力。明确登记的别名可规范化为 canonical ID；相似名称、猜测版本或同系列模型不能自动当成同一个模型。

| 结果 | 定义处理 | 返回主 Agent 的信息 |
| --- | --- | --- |
| inherit | 保存继承政策 | 已创建/更新，未写死当前模型名 |
| explicit 名称准确可用 | 保存规范 ID 和用户指定来源 | 已创建/更新、实际模型 |
| model_not_found | 不启用该未解决定义 | 原指定名称、目录修订版、可用候选和缺失原因 |
| model_ambiguous | 不猜测选择 | 匹配的可见候选，需要消除歧义 |
| model_unavailable / capability_mismatch | 保留问题，不静默切换 | 当前原因与满足条件的可见候选 |
| 用户明确要求 auto | 保存 Auto 政策 | 可路由范围；没有合格候选时返回问题 |

不可用名称返回当前主 Agent，而非尝试调用不存在的模型。主 Agent 继续使用当前已解析模型，决定解释、请求用户选择、在既有替代授权内重提交或先完成其他角色。用户明确指定模型但没有授权替代时，LLM 可以推荐候选，不能自行改成 inherit、Auto 或另一模型后启用。

模型存在和动作合法时，直接创建/修改并返回配置 Item。创建有关键阻碍时保持该定义未创建，或保存 `pending_resolution` 草稿（不能被委派调用）；UI 必须区分草稿与已启用定义。用户之后选择有效模型再完成创建。

## 5. 保持 Agent 循环，避免固定处理流程

```text
主 Agent 读取用户要求
  ↳ 按需加载短设计指令，提交定义动作
  ↳ 成功：展示已创建结果，并可继续其他工作
  ↳ 失败：消费类型化反馈，修复、解释、澄清或继续其他定义
```

此循环的技术校验是必需执行边界，但不强制“设计模型 → 模型选择模型 → 审批模型 → 保存模型”的串行流程，也不为普通创建生成任务图。模型可以在一个动作中提交多项独立定义，并按每项结果继续。

独立定义允许部分成功，返回每项 status、definition_id/version、canonical_model_policy 或 errors；某项模型缺失不回滚其他已成功项。互相依赖或用户明确要求整组成功的定义先校验整组，再原子提交元数据。request_id 和每项稳定请求 ID 用于幂等，反馈丢失时先查状态而不是再次创建；更新用预期版本避免覆盖另一回合的修改。

可确定的格式/引用错误允许有预算的修复；需要用户授权的模型替换不靠重复 LLM 调用“修复”。重复相同失败后停止重提交并说明问题。失败本身不增加权限、实例数量或执行预算。

## 6. 需要验证的行为

- 用户只要求职责：定义默认 inherit，不自行选模型。
- 用户选具体子模型：准确保留、目录校验成功后保存；不存在时返回当前 LLM 并询问/推荐。
- 用户允许替代：LLM 只在该授权和当前目录内选择，记录依据。
- 创建多项时部分失败：准确说明成功和未解决项，再次提交不重复创建。
- 同名定义或并发更新冲突：不静默替换，保留版本与反馈。
- 角色指令简短，技能按需加载；不复制所有工具 schema 和共同政策。
- 创建配置不误触发实际委派、规划或文件写入。
